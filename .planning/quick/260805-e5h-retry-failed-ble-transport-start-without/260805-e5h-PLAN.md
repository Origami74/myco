<objective>
Re-arm a BLE transport that failed to start because the Android radio bridge had not
been injected yet — without restarting the node.

Purpose: F-01 (blocking, demo-critical). The Android foreground service injects its BLE
bridge ~620ms AFTER the node starts, so `io.listen()` fails with "BLE radio not
available", the transport marks itself `TransportState::Failed`, and nothing ever
restarts it. BLE is dark after every fresh app start — no scanning, no advertising, zero
BLE peers — until the user manually restarts the node. Two phones in the same room with
no shared network do not connect at all.

Output: a generic transport restart supervisor in fips, driven by the node's existing 1s
maintenance tick, plus deterministic unit tests and on-device confirmation on both phones.
</objective>

<design_decision>
The planning context offered two shapes. **Shape (a), retry supervision, is chosen; shape
(b), wake-on-radio-arrival, is rejected.**

Why (a): `TransportState::Failed.can_start()` already returns `true`
(`transport/mod.rs:330-335`, asserted at `:1396`) — the capability to restart a failed
transport is sanctioned and unexercised. The node already runs a 1s maintenance tick
(`node/handlers/rx_loop.rs:252`, `node.tick_interval_secs` default 1) that computes
`now_ms` and drives a dozen `poll_*` / `check_*` helpers. Supervision is one more entry in
that list. No new signalling, no new task, no io-layer coupling.

Why not (b): `set_android_ble_bridge()` waking a parked transport would couple
`transport/ble/android_io.rs` back into node lifecycle, and is BLE/Android-specific — the
opposite of what a fips maintainer accepts. The latency it would buy is negligible: the
race is 620ms and the first retry is scheduled 1s after the failure, so (a) closes the
window within ~1-2s of the bridge appearing. (b) is not needed and is not implemented.

**Two findings from reading the tree change what the fix must be:**

1. **Failed handles are dropped today, not retained.** `Node::start()` at
   `lifecycle.rs:1238-1261` only does `self.transports.insert(...)` on the `Ok` arm; the
   `Err` arm warns and lets the handle drop. So a supervisor scanning `self.transports`
   for `Failed` entries would find nothing — which is exactly why
   `grep -rn "TransportState::Failed" src/node/` returns no matches and why nothing could
   have retried. The handle must be **retained** for supervision to be possible at all.

2. **Retention must be quarantine, not in-place.** `self.transports` has ~50 consumers
   across `node/`, `node/handlers/` and the snapshot path. Admitting a non-operational
   entry into that map on release day means auditing all of them. Instead, failed handles
   go into a separate `pending_transports` vector, invisible to every existing data-plane
   path, and are moved into `self.transports` only once `start()` returns `Ok`. Zero
   existing consumer changes behaviour; a transport that never comes up is exactly as
   invisible as it is today.

**And one trap that must be honoured:** only `BleTransport` ever assigns
`TransportState::Failed` (`transport/ble/mod.rs:220` — verified, it is the sole assignment
in `src/transport/`). UDP and TCP leave `state` at `Starting` when `start_async` errors
(`udp/mod.rs:197`, `tcp/mod.rs:214`), and `Starting.can_start()` is `false`. So the
supervisor must quarantine on `handle.state().can_start()`, never on "start returned
Err". A UDP bind failure stays dropped as today; if a transport later adopts the
`Failed`-on-start-error convention it gains supervision for free. That is the generic
rule, stated by capability rather than by transport type.

**Scoped out, deliberately:** the partial-failure case at `ble/mod.rs:226-260`, where
advertise and scan failures only `warn!` and the transport still reaches
`TransportState::Up` at `:262` — a transport can report `Up` while advertising and
scanning are both dark. It does not bite F-01 (the field failure is `listen()`, which
returns early before advertise/scan are attempted), and converting those warns into start
failures would mean re-running `io.listen()` on a transport that already has a live
acceptor and a spawned accept loop — an unbounded-risk change on release day. Task 2
documents the limitation at the call site and records the follow-up.
</design_decision>

Two module constants: `RESTART_BASE_MS = 1_000` and `RESTART_MAX_MS = 30_000`, each with a

`pub(super) struct PendingTransport` holding `handle: TransportHandle`, `attempts: u32`,
`retry_after_ms: u64`. Mirror the `RetryState` idiom in `src/node/retry.rs`: `backoff_ms`
computes `RESTART_BASE_MS` shifted left by `attempts` via
`1u64.checked_shl(attempts).unwrap_or(u64::MAX)` and `saturating_mul`, then `.min(RESTART_MAX_MS)`;
`is_due(now_ms)` is `now_ms >= self.retry_after_ms`; `schedule_after_failure(now_ms)`
sets `retry_after_ms = now_ms + backoff_ms()` then `attempts = attempts.saturating_add(1)`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Kotlin BLE radio -> fips transport | An externally-owned radio whose availability the node does not control crosses into transport lifecycle |
| node tick -> transport start | A periodic, unattended code path now invokes `start()` on handles the node retains |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
