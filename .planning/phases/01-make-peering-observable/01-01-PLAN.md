<objective>
Turn "which peers does this phone know about, and what is actually true of each one" from
four separate arrays the UI hand-joins into one merged, ordered, npub-keyed `peers` array
computed once in Rust and rendered on the Dev tab.

Purpose: DIAG-01, DIAG-03, DIAG-04 need a single row model that survives an unresolved
advert (D-09), carries five states (D-10) and orders by state-then-recency (D-11). D-19
locks that merge to Rust. Everything later in this phase (radio truth, attempt log, the
screen rebuild) hangs off this row.

Output: `PeerDiagnosticView` + `AppState.peers` in Rust, a unit-tested pure merge module,
the Kotlin parse, and a Dev-tab peers card rendering real state / last-seen / transport.
</objective>

Public surface: `pub fn merge_peers(...) -> Vec<PeerDiagnosticView>` taking borrowed slices of
the already-fetched data — the `PeerView` list, `&[BlePeer]`, `&[BleAdvert]`, `&[CircleContact]`,
`&[PairRequestView]`, `&[OutboundPairView]`, `&[String]` for `reachable_npubs`, and a
`now_ms: u64` — plus a private `peer_state_rank(state: &str) -> u8` giving the D-11 ordering
weight (connected 0, reachable-via-relay 1, seen-unidentified 2, paired-offline 3,
unreachable 4).

Build the merge in the order RESEARCH's Pitfall 4 prescribes, because npub-first grouping
silently loses the unresolved rows D-09 requires:
1. Start from the peer views / `ble_peers` as the base identity set, keying each row on its
   `npub` when non-empty, else on its `node_addr_hex`.
2. Union in the adverts as additional not-yet-resolved rows keyed by BLE address, but first
   attach any advert whose address is already attributed to an existing row onto that row
   (its `rssi`, `psm` and `ble_addr`) instead of creating a second row — that attribution map
   is extended in plan 01-03 once the attempt log can resolve an address to a node address.
3. Union in every npub that appears only in the Circle, the incoming pair requests or the
   outbound invites, so a pairing with no radio contact yet still has a row.
4. Left-join the Circle name, the pair state and the relay reachability onto rows that have an
   npub.
5. Assign `state` last: `connected` when the peer view says connected; else
   `reachable-via-relay` when the npub is in `reachable_npubs`; else `seen-unidentified` when
   the row has no npub; else `paired-offline` when the npub is in the Circle or has a pending
   pairing; else `unreachable`.
6. Sort by `peer_state_rank`, then `last_seen_ms` descending, then `key` ascending — a total
   order, so two polls over the same data always produce the same sequence.

Every peer-supplied string that reaches the view (`name`, `display_name`) is truncated to at
most 64 characters in Rust before it crosses the FFI; the Kotlin `short()` helper is a second
line of defence, not the only one. The view carries no pairing credential — do not read the
credential field of `PairRequestView` here at all.
