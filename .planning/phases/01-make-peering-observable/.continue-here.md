<decisions_made>
- **Lane disambiguation lives entirely in Kotlin + myco-core, zero fips diff.** Wi-Fi Aware rides
  fips's UDP transport, so `link_info.transport_type` is structurally `"udp"` for both Aware and
  the LAN/AP lane. fips cannot tell them apart, and teaching it to would be the Myco-specific
  coupling CLAUDE.md forbids upstream. The lane is only knowable at the Kotlin push site.

- **F-01 fixed by retry supervision, not by restarting the node.** Restarting the node is the
  manual workaround; fips commit `9121925` records that bouncing it "drops every peer, every
  session, and every route." The fix retains a failed transport handle in a quarantine vector and
  retries `start()` on the existing 1 s tick, gated on `handle.state().can_start()` — generic by
  capability, so UDP/TCP (which stay in `Starting`, where `can_start()` is false) keep today's
  drop behaviour instead of spinning against `AlreadyStarted`.

- **`git.branching_strategy` set to `"phase"`.** It was `"none"`, which is why this phase's work
  originally landed on `main` and had to be moved onto a branch after the fact.

- **A fact the code cannot observe renders as `unknown` or an em-dash, never as a confident
  value.** This is the phase's standing prohibition and it has already caught two violations
  (a fabricated `"ble"` transport default; a doc comment asserting Android's only transport was
  BLE while the device was demonstrably on UDP). Enforce it.
</decisions_made>

<field_findings>
Recorded in `.planning/phases/01-make-peering-observable/01-FIELD-FINDINGS.md`. All observed on
real hardware. **These are Phase 2 peering faults, not Phase 1 instrumentation faults — do not
fix them in Phase 1.**

- **F-01 — FIXED.** The Android foreground service injected the BLE bridge ~620 ms *after* the
  node started, `io.listen()` failed with "BLE radio not available", the transport was marked
  `Failed`, and its handle was dropped rather than retained — so nothing could ever retry it.
  BLE was dark after every fresh app start until a manual node restart. Now recovers in ~1.2 s.

- **F-02 — OPEN.** PSM never resolves for at least one FIPS advertiser, so no L2CAP attempt is
  made (`PSM not in advert yet (awaiting scan response)`, repeating for minutes). **01-03's
  attempt log is the instrument built to characterise this.** Peer identity unconfirmed — the
  phones use resolvable private addresses, so they cannot be correlated by MAC.

- **F-03 — OPEN, code-read only.** `AwareRadio.onAttachFailed()` only logs, with no retry, but
  `registerAvailability()`'s `ACTION_WIFI_AWARE_STATE_CHANGED` receiver re-attaches on
  availability transitions, so Aware is less exposed than BLE was.

- **F-04 — OPEN, NOT YET WRITTEN TO THE FINDINGS FILE.** `reachable-via-relay` is derived solely
  from `peer_relays.connected_npubs()` (`myco-core/src/content.rs:962`), i.e. from whether a
  keepwarm WebSocket to `ws://<npub>.fips:4870` happens to be open — not from mesh routing. So it
  blinks in and out for peers that are continuously routable. Observed same-session: Pixel 2
  connected / 5 failed, Samsung 2 connected / 16 failed, all `ENETUNREACH`, including to a peer
  the UI showed as directly BLE-connected. Meanwhile `ping6` across the mesh was 0 % loss both
  directions. The deeper gap: `ControlReadHandle` exposes only `peer_views()` — fips publishes no
  routing/reachability API at all, so Myco has nothing to ask. **Ask the user whether to log this
  as F-04 before starting 01-03.**
</field_findings>

## Critical Anti-Patterns

| # | Anti-pattern | severity | What happened |
|---|---|---|---|
| 1 | Reading `adb logcat` without filtering to the current pid | blocking | The buffer retains lines from pre-reinstall processes. A stale `MycoBleRadio` line from a dead pid was briefly read as evidence the current build was scanning. Always resolve `adb -s <serial> shell pidof app.myco` and filter `logcat -d --pid=<pid>`, and check the buffer covers the process's whole lifetime before concluding "no such log line exists". The two phones also have different timezones — correlate on the `myco` tracing timestamps (UTC), never logcat wall-clock. |
| 2 | Wiping app data during on-device verification | blocking | "Fresh install" was taken literally enough to clear the Pixel's data. `identity.nsec` regenerated, the device got a new node identity mid-session, its Circle was emptied, and the two phones silently un-paired — the Samsung kept showing the Pixel's dead old identity as a red `unreachable` row. Cost a re-pair and produced misleading peer observations. Use `adb install -r`, which preserves data; never `pm clear` or uninstall/reinstall. Verify afterwards with `run-as app.myco ls -la files` that `identity.nsec` kept its old mtime. |
| 3 | Assuming a fips-tree edit is captured by a fips-pop commit | blocking | `reference/fips` is a symlink to a separate repo. Committing in fips-pop leaves fips edits uncommitted and invisible. See `<repo_layout>`. |
| 4 | Presenting an inferred value as an observed peer fact | blocking | The phase's standing prohibition. Already caught twice: a `"ble"` transport default fabricated whenever fips reported no resolved link, and a doc comment asserting BLE was Android's only transport while the device was demonstrably on UDP. A fact the code cannot observe renders as `unknown` or an em-dash. |
| 5 | Fixing a Phase 2 peering fault inside Phase 1 | warn | Phase 1 makes faults visible; Phase 2 fixes them. F-02/F-03/F-04 are out of scope here. F-01 was fixed only because the user explicitly redirected mid-phase. |
| 6 | Committing straight to `main` | warn | `git.branching_strategy` was `"none"`, so 9 commits landed on `main` and had to be moved. Now set to `"phase"`; confirm the run is on `gsd/phase-01-make-peering-observable` before committing. |
