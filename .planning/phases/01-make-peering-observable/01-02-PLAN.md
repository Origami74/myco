<objective>
Replace the two radio-status values the app currently guesses at with values it actually
observes, so DIAG-05 becomes literally true instead of usually true.

Purpose: `AppState.ble.scanning` is computed from other flags today, and `WifiAwareStatus`
has no scanning field at all. Both can read "active" while the scan loop is dead or throttled
by Android's roughly five-scans-per-thirty-seconds limit — the exact condition the demo needs
to be able to see. D-07 makes these facts the first thing on the screen at zero peers, so they
have to be true.

Output: a pushed-not-polled observed scanning/advertising signal for BLE through the existing
fips bridge, an observed discovering signal for Wi-Fi Aware through the Aware JNI seam, and an
explicit unknown state for each fact that cannot be observed.
</objective>

## Planner assumptions and breadcrumbs

- **Aware "actively scanning" source (Claude's Discretion, CONTEXT.md; RESEARCH Assumption A1).**
  Pinned to `publishSession != null || subscribeSession != null` in `AwareRadio` — the two sessions
  start and stop together in the current lifecycle, so a single boolean does not under-report.
  Labelled "discovering" on screen, since Aware has no literal scan call.
- **Unknown is a first-class value.** Each fact ships with a `*_known` sibling boolean rather than
  collapsing unknown into false. This is what makes the P1 prohibition checkable and keeps the
  existing `bleScanning` consumers (`CircleScreen.kt`, `DevScreen.kt`) compiling untouched.
- **fips genericity.** The fips diff is confined to `android_io.rs` — the module that already owns
  the Android radio bridge and already exposes exactly this shape (`deliver_scan` pushes,
  `advert_views` reads). Two atomics plus four methods, no Myco types, no new trait method on
  `AndroidRadio`. It stands alone as an upstream PR ("surface observed radio state on the Android
  BLE bridge").
- **Edge coverage.** This plan resolves DIAG-05 adjacency and DIAG-05 empty. DIAG-05 ordering (the
  fixed self-check row set) is a render concern resolved in plan 01-04. Zero dropped.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Android radio callback thread to Rust core | Kotlin pushes radio-state transitions across JNI on the radio's own callback thread |
| Rust core to Kotlin UI | The radio facts become the first thing the diagnostics screen asserts |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Denial of service | `BleRadio.startScanning` / `handleScanResult` callback thread | medium | mitigate | The bridge setters are a single relaxed atomic store — no lock, no channel send, no allocation — so a push can never stall the scan callback or the advertise callback. |
| T-02-02 | Tampering (data integrity) | observed scanning flag going stale | medium | mitigate | The flag is pushed from every transition site including the failure and retry paths, and a bridge that fails to resolve reports unknown rather than the last-seen value, so a dead scan loop cannot leave a stale "active" on screen. |
| T-02-03 | Spoofing | the pushed booleans | low | accept | The pusher is the app's own Kotlin radio in the same process and trust domain as the reader; a compromise at that layer already owns the whole app. |
| T-02-04 | Information disclosure | new JNI exports | low | accept | Both exports carry a single boolean and no identity, address or credential material. |
| T-02-SC | Tampering | npm/pip/cargo installs | low | accept | Zero packages installed in either Cargo workspace or the Gradle module; RESEARCH.md's Package Legitimacy Audit records no new dependencies, so there is no install step to gate. |
</threat_model>
